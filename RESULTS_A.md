# Project A — Salary tax comparison

The calculator returns both regimes and the signed amounts behind taxable income and payable tax. In the boundary example, FY 2024–25 gross salary of ₹7,75,100 produces ₹59,820 old and ₹100 new. With the same inputs in FY 2025–26, new-regime tax is ₹0. The model meets the salary-only brief for the claims represented in the input schema. Section 80D inputs cover eligible insurance premiums. A single HRA tuple covers a period with one applicable city rate.

All 30 salary scenarios matched the official portal in both regimes. I used the Advanced Calculator under the 1961 Act, AY 2025–26, for a resident under 60 with salary only. The fixtures retain the displayed Total Tax on Income and its normalized result. The portal reports tax before statutory payable rounding and separately adds filing interest and fees. I compared the tax line and applied §288B. At gross ₹7,75,100 it displayed ₹104 before rounding, which corresponds to ₹100 payable. [Official reference](https://eportal.incometax.gov.in/iec/foservices/#/TaxCalc/calculator)

The parser gained deterministic checks for stated residency, conflicting year references, and selected ambiguous salary expressions. On the same 50 descriptions, expected status moved from 35 to 37, correct clarification field from 7 to 13 out of 24, incorrect acceptances from 3 to 2, and request errors from 10 to 9. The follow-up accepted one CTC input and one contradiction about gross pay. The latency medians including only completed cases were 3.060 s and 4.256 s. These runs do not establish extraction accuracy for every amount.

## Change review

The 2025 change affects new-regime slabs and Section 87A. For the same boundary case, the reviewed compiled engine produced ₹59,820 old and ₹0 new on ten attempts. The FY 2025–26 query-time run returned the same wrong raw totals, ₹59,800 and ₹15,010, on all six replies it received. Each failed trace reconciliation. The other four requests had transport failures. Six consistent wrong replies show why repeatability alone does not establish correctness. Existing code was built across both years, so there is no controlled elapsed migration time for the hand-written or query-time versions. The initial Gemini Python generation ran in 7.235 s and 8.795 s for the respective FYs in the observed shell runs. These are generation times and exclude subsequent review. Review found missing surcharge, incorrect old slabs, incorrect HRA base, and malformed traces. In FY 2025–26, the generated parent insurance cap also used the taxpayer's age. Each could yield wrong answers without a Python exception.

The ten-repeat FY 2024–25 median times were 0.169 ms for hand-written rules, 0.050 ms for reviewed compiled rules, and 3.392 s for query-time Gemini (including rejections). Both local paths recorded zero external model cost. The 30-case FY 2024–25 Gemini run had a 2.122 s median across all attempts and USD 1.165 projected per 1,000 metered replies at paid rates. Usage was available for 15 replies. Gemini requests used a free-tier project. The six metered FY 2025–26 replies would project to USD 1.268 per 1,000 at paid standard rates, excluding failed calls without usage metadata. Timings reflect this machine and run rather than a production service level. [Gemini pricing](https://aistudio.google.com/docs/pricing#gemini-3.1-flash-lite)

## Deployment design

I would use Gemini for extraction, then ask the taxpayer to confirm the year, residence, gross pay and deductions before evaluating versioned local rules. Clarifications belong at the boundary because the parser accepted incomplete inputs twice even after validation. The query-time tax experiment had no accepted responses on its first repeated case. The local engine returns a clause-linked breakdown and uses no external API requests. Gemini-generated tables can accelerate a draft update, with human source review and the regression suite as release gates.

For a Budget update, preserve the old policy file, introduce a version tied to the effective financial year, and run both versions on threshold fixtures before deployment. Record the official calculator observations and investigate discrepancies before approving the change. The test oracle implements slabs as marginal-rate changes. The official portal independently verified all 30 logged salary scenarios for the first year. The second-year threshold cases use the local test oracle.
